# Диагностика Kotlin/Spring Backend

## Scope и исходные данные

Определи ожидаемое и фактическое поведение, конкретный вход, затронутую версию и среду. Изучи применимые инструкции, build/config и ближайший execution path. Начинай с наиболее вероятной причины по имеющимся данным; не проводи аудит всего backend.

Запрос только на диагностику означает исследование и отчёт без изменения приложения. При запросе на исправление вноси изменения в его scope. Отдельный AGENTS.md из набора и другие skills не обязательны; доступные профильные skills подключай для конкретного механизма, например ORM или Spring proxies.

## Получи проверяемый сигнал

Предпочитай минимальный тест, локальный HTTP/CLI-запуск или replay обезличенного payload, который обнаруживает именно заявленный дефект. Сначала изучить код для выбора такой проверки нормально. Проверка «не упало» недостаточна, если ошибка — неверный результат или лишние запросы.

Зафиксируй вход, команду и результат до исправления. Уменьшай пример только пока это помогает различать причины; сохраняй значимые transaction boundaries, число callers, данные и concurrency. Не трать время на абсолютную минимальность уже полезного воспроизведения.

Для нестабильного сбоя фиксируй seed, условия, число запусков и частоту ошибок; увеличивай нагрузку только в изолированной среде с ограничением времени/параллелизма. Один удачный запуск не доказывает устранение race condition.

## Если воспроизведение недоступно

Продолжай по коду, stack trace, логам, конфигурации и истории изменений. Разделяй наблюдаемые факты, выводы из execution path и гипотезы, требующие запуска. Недоступный DB engine или стенд не заменяй mock-проверкой с заявлением, что интеграция подтверждена.

Запрашивай только недостающие данные, которые действительно различат вероятные причины. Если доказательств недостаточно для изменения поведения, предложи точную следующую проверку. Очевидное и обоснованное исправление допустимо в разрешённом scope, но явно отметь отсутствие runtime-подтверждения.

## Проверяй причины по одной

Для вероятной причины сформулируй предсказание: какое наблюдение её подтвердит или опровергнет? Используй targeted test, debugger, SQL/logging или чтение конкретного участка кода. Меняй один существенный фактор за раз и пересматривай вывод при противоречащих данных. Альтернативы добавляй, когда они меняют проверку или решение; обязательного количества гипотез нет.

Для Kotlin/Spring учитывай только относящиеся к пути механизмы: proxy/self-invocation, rollback и commit timing, persistence context/N+1, thread/Reactor context, cancellation, повторную доставку и concurrent updates. Наличие аннотации или ключевого слова само по себе не доказывает поведение runtime.

## Регрессии производительности

До оптимизации зафиксируй метрику и условия: latency/throughput, query count/plan, allocations, pool saturation или lock contention. Сравнивай одинаковые входы и нагрузку с учётом прогрева JVM и состояния cache. Выбирай профилирование или измерение, которое различает предполагаемые причины; не подменяй измеренное улучшение интуицией.

## Исправление и завершение

При разрешённом исправлении добавь regression test на границе, где проявляется дефект, если он даёт полезную защиту. По возможности проверь его падение до изменения и прохождение после. Не проверяй упрощённый mock-сценарий, исключающий сам механизм ошибки.

Повтори исходный сценарий, затем необходимые соседние проверки. Удали только собственную временную instrumentation и ненужные диагностические артефакты, сохранив чужие изменения. Заверши, когда запрошенное исправление выполнено и доступные проверки закончены; недоступные проверки перечисли явно.

Используй локальные/изолированные ресурсы в пределах разрешённого доступа. Не повторяй платежи, webhooks или изменяющие запросы к общей среде ради воспроизведения без соответствующего разрешения. Не сохраняй и не выводи credentials или лишние персональные данные из логов и replay payloads.

## Результат

Сообщи причину и подтверждающее наблюдение либо наиболее вероятную гипотезу с ограничением. Для исправления добавь, что изменено, какие проверки выполнены и что осталось непроверенным. Не объявляй проблему воспроизведённой или исправление подтверждённым без соответствующих результатов.
