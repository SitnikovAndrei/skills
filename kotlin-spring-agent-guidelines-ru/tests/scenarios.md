# Поведенческая проверка skills

Используй изолированную копию небольшого Kotlin/Spring проекта с нужным стеком и тестами. Вход должен содержать код, build files и контракты, достаточные для задачи. Не подключай production DB или реальные внешние сервисы. Сценарии ниже ещё не являются выполненными проверками.

Для сравнения выполняй один запрос на одинаковом исходном состоянии в отдельных сессиях с целевым skill и без него. Сохраняй одинаковые модель, настройки и проектные инструкции. Для проверки автоматического выбора не называй skill в запросе. Не показывай агенту ожидаемый результат из таблицы; оценивай итоговый diff/отчёт, проверки и побочные изменения.

| Сценарий и вход | Запрос агенту | Ожидаемый выбор и наблюдаемое поведение |
|---|---|---|
| Простой CRUD: Controller → Service → Repository, без сложного домена | Добавь optional description в создание товара, сохрани совместимость API | Spring; persistence при изменении схемы. Рабочий контракт и нужная миграция, без обязательного добавления ports, handlers и ServiceImpl |
| Pageable список заказов с lazy collection и подтверждённым N+1; несколько заказов с одинаковым sort key | Устрани N+1, сохрани размер и порядок страниц | Persistence, testing при необходимости. Ограниченный query count, стабильная сортировка с tie-breaker и корректная страница; без глобального EAGER или некорректного collection fetch join |
| Public transactional method вызывается внутри того же bean, proxy mode; контракт требует атомарности | Исправь частичное сохранение при сбое второго шага | Spring. Найден фактический путь self-invocation, восстановлен rollback; тест проходит через реальную границу, а не только mock |

Задача выполнена по доступному коду/контракту без требования установить остальные skills или шаблон AGENTS.md |

## Дополнительные сценарии для диагностики и ревью

| Сценарий и вход | Запрос агенту | Наблюдаемое поведение |
|---|---|---|
| Diff без stylistic defects; в acceptance criteria есть запрет отмены оплаченного заказа, код запрещает только доставленный; тесты повторяют реализацию | Проведи ревью реализации по этим требованиям | Найдено конкретное расхождение с требованием, несмотря на зелёные тесты; нет выдуманных требований или изменений файлов |
| Набор обёрток: одна лишь переименовывает вызов, другая с аналогичным телом владеет @Transactional boundary | Оцени, какие слои можно упростить | Обоснована разница между лишним forwarding и границей транзакции; слои не объявлены одинаково бесполезными по числу строк |
| Stack trace, код и конфигурация показывают вероятную ошибку; DB/стенд недоступны | Диагностируй сбой по этим артефактам | Анализ продолжается без бесконечного требования воспроизведения; выводы привязаны к данным, runtime-гипотезы отмечены, предложена различающая причины проверка; приложение не изменено |
| Замедление списка заказов воспроизводится на локальной БД, исходный query count известен | Найди и исправь причину замедления | Измерены сопоставимые условия до/после; исправлена причина, повторён исходный сценарий, временные debug logs удалены; ускорение не объявлено без измерений |

Фиксируй для каждого прогона: версию skills, модель/настройки, исходные артефакты, выбранные skills, итоговый diff или отчёт, команды и результаты проверок, лишние изменения, оставшиеся ограничения. Пограничные случаи выбора повторяй, если единичный результат неустойчив.

Исправляй инструкции по наблюдаемому дефекту. Не подгоняй их под конкретное имя класса или формулировку одного запроса. После изменения повтори проваленный сценарий и затронутые соседние случаи; новые задачи используй для проверки обобщения.
